# INITIAL AUDIT — vpn-private-poster

Дата: 2026-08-22
Состояние: до рефакторинга (v31, `poster_private.before_refactor.py`)

## 1. Текущая архитектура

Один монолитный скрипт `poster_private.py` (631 строка, v31):

1. Загрузка ключей из 3 публичных источников (GitHub raw).
2. Очистка строк, дедупликация, ограничение 1000 ключей.
3. DNS-префильтр + TCP-проверка параллельно (30 потоков).
4. Xray-верификация топ-30 ключей на регион (только VLESS).
5. Группировка по регионам (TLD-определение), сортировка по RTT.
6. Запись файлов подписок `<Region>_partN_sub.txt` во временную папку.
7. Push файлов в git-репозиторий (отдельный clone `repo_clone/`).
8. Отправка обложки + кнопок с ссылками в закрытый Telegram-канал.

Запуск: GitHub Actions `schedule.yml` каждые 6 часов, ubuntu-latest, Python 3.10.

## 2. Как собираются источники

`SOURCE_URLS` — три статических URL:
- `vpn-vless-configs-russia/all_new.txt` (githubmirror)
- `bypass-rkn-blocks/obhod_WL`
- `bypass-rkn-blocks/obhod_BL`

Каждая строка чистится: обрезка по пробелу/табуляции/`#`/`|`, `&amp;` → `&`.
Ограничение: максимум 1000 ключей (константа `MAX_KEYS_TO_CHECK`).
Источник каждой конфигурации НЕ сохраняется (только сам ключ).

## 3. Как выполняется проверка

- `prefilt_key`: извлекает host:port, разрешает DNS.
- `tcp_check`: TCP-connect с таймаутом 3 сек, замер RTT.
- `xray_check_key`: для VLESS собирает Xray-конфиг, HTTP-inbound на порту 1080,
  контрольный запрос через `https://api.ipify.org?format=json`.
- Fallback: если Xray не дал результатов — используются TCP-результаты целиком.

Критические проблемы проверки:

1. **TCP fallback**: `if not verified: return working` — ключи, прошедшие только
   TCP, публикуются как рабочие. Нарушает главный принцип ТЗ.
2. **Только VLESS**: Xray-проверка возвращает False для всех не-VLESS ключей.
   VMess/Trojan/SS публикуются по TCP без протокольной проверки.
3. **Фиксированный порт 1080** для всех Xray-процессов — параллельный запуск
   даёт конфликт портов (хотя по факту проверка последовательная).
4. **`ss://` → `vless://` конвертация** (строка 86) — критический баг:
   заменой префикса протокол не меняется, такие ключи заведомо нерабочие,
   но проходят TCP-проверку и попадают в подписки.
5. **`replace_hosts_in_key`** подменяет hostname на `dostyp_k_internety` —
   ломает VLESS Reality (SNI/pbk/sid остаются от старого host), TLS-сертификаты.

## 4. Как создаются файлы подписок

`create_subscription_files`: для каждого региона (Europe/Asia/USA/Russia/Other)
ключи режутся на чанки по 100, hostname заменяется на `dostyp_k_internety`,
пишутся файлы `<Region>_partN_sub.txt`. В dry-run — во временную папку.

Без manifest, без метаданных о проверке, без атомарной замены:
при падении между записью и пушем репозиторий может остаться с пустыми файлами.

## 5. Как выполняется push

`push_to_repo`: клонирует репозиторий по URL с токеном
(`https://kort0881:<GH_TOKEN>@github.com/...`), копирует файлы в `checked/`,
commit + push (с pull --rebase при конфликте).

Проблемы:
- Токен в URL может попасть в stderr git при ошибке → в логи.
- Клонирование с `--depth=1` — нормально для автообновления.
- При пустом результате `checked/` не очищается (git add -A добавит удаления
  только если файлов нет в file_meta — их копирование пропускается, удаления
  не происходит — фактически старое остаётся, но это не контролируется явно).

## 6. Как отправляются сообщения в Telegram

- `send_photo`: обложка `cover_private.jpg` с caption (HTML).
- `send_message` + `build_keyboard`: кнопки-ссылки на raw-файлы подписок,
  батчами по 100 кнопок.
- DRY_RUN: сообщения не отправляются, печатается `[DRY]`.
- Бот-токен в `TELEGRAM_BOT_TOKEN`, канал в `TELEGRAM_PRIVATE_CHANNEL`.

## 8. Причины, по которым workflow может не работать

1. Xray не загружен/не кэширован — верификация молча пропускается,
   публикация уходит на TCP-результатах.
2. `timeout-minutes: 30` может не хватить при 1000 ключах + Xray.
3. Отсутствует `TELEGRAM_ADMIN_CHAT_ID` (новый секрет по ТЗ) — пока не нужен,
   добавится с AI-контуром.
4. Репозиторий-источник `vpn-vless-configs-russia` может отдавать битые/пустые
   списки — скрипт тогда завершится с ошибкой (это правильно).
5. GitHub API rate limit на raw.githubusercontent не применяется, но сетевые
   сбои возможны — retry есть (3 попытки).

## 9. Причины публикации нерабочих конфигураций

1. **Главная**: TCP-fallback — публикация без протокольной проверки.
2. `ss://` → `vless://`: протокольно невалидные ключи проходят TCP.
3. replace_hosts: после подмены hostname конфигурация не перепроверяется,
   SNI/Reality-параметры не синхронизируются — реально нерабочие ключи
   публикуются как рабочие.
4. Не-VLESS не проверяются вообще (см. п.3 раздела 3).

## 10. Что будет исправлено (по ТЗ, приоритеты P1+P2)

- Удаление ss→vless конвертации; поддержка vless/vmess/trojan/ss/hysteria2/hy2.
- Уровни проверки L1-L4, запрет TCP-fallback, `protocol_passed` обязателен.
- Xray: свободные порты, уникальные tmp-диры, таймауты, лимит параллельных,
  безопасные ошибки.
- `config/settings.yaml` + override через env.
- Отчёты: `data/current_report.json`, `data/previous_report.json`,
  `data/diagnostics.jsonl`, `src/report_diff.py`.
- `checked/manifest.json`, атомарная замена, защита от пустого результата.
- replace_hosts по умолчанию false.
- Маскирование URL/секретов в логах.

## 11. Что осталось ограничением

- Hysteria2: UDP/QUIC-проверка невозможна в GitHub Actions (нет UDP-сокетов
  нужным образом) — такие ключи получают `check_level=tcp_only` и не попадают
  в `verified`.
- Протокольная проверка VMess/Trojan/SS через Xray — будет реализована;
  если Xray-бинарник недоступен, честно фиксируется `protocol` недоступен.
- GitHub Actions не даёт гарантированного `-assets` пути для Xray
  (geoip/geosite) — Xray может требовать assets; учтено в конфиге проверки.
- Интерактивные кнопки админа (AI-контур, P3) требуют постоянно работающего
  процесса — в рамках GH Actions нереализуемо; решение будет описано
  в LOCAL_TESTING.md при реализации P3.
